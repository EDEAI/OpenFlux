# OpenFlux 外部群会话接入与待分配任务改造方案

版本：v0.1  
日期：2026-09-09  
状态：产品规则已按本轮讨论收敛，技术接口为待实施、待联调方案。  
范围：OpenFlux 客户端与本地 Gateway；列出需要 Router 配合的契约，不包含第三方平台适配实现。

本文基于当前本地工作区和 `docs/router-integration-guide.md` 的只读检查。工作区存在其他未提交改动，本文不是对远程分支、线上 Router 或全部平台能力的实现认证。本文新增的字段、模块和操作名称均为建议，不代表现有接口。仅生成本地方案文档，不修改业务代码，不提交 Git，不部署或发布。

## 1. 核心决策

**群首次有效请求 → Flux 创建待分配任务 → 用户选择 Project/Agent → 建立固定专用会话 → 后续请求自动归入该会话并排队。**

本方案采用以下已确定规则：

1. 不要求用户提前给群配置 Project/Agent；由首次请求触发待分配入口。
2. 首次请求能够送达的前提是账号、执行设备及群访问关系已经通过 Router 验证。账号绑定与任务归属分配是两个不同步骤。
3. 未分配时只保存请求、展示待分配卡片，不调用模型执行任务，不临时放入默认 Agent。
4. 用户只选择归属的 Project 或 Agent，不额外选择已有会话。系统自动创建一个专用于该绑定的 Flux Session。
5. 同一绑定范围的后续请求固定使用这个 Session：空闲执行、忙碌排队。用户说“新任务”只新增执行项，不新开聊天会话。
6. 第一版不支持从飞书/钉钉新开或切换 Flux Session，也不根据平台 `thread_id` 自动拆分 Session。
7. 补充当前任务、停止、澄清答案、审批和状态查询，按各自语义处理，不能全部塞入普通任务队列。
8. 每项任务保留独立来源、权限、执行身份和回复位置。共享 Session 不代表混用发起人身份或审批权限。

“待分配任务”是用户看到的卡片名称；技术上它聚合的是同一外部会话绑定范围内的一组未分配请求，不是全公司所有人可以任意认领的公共任务池。

## 2. 唯一映射与第一版边界

### 2.1 哪些消息共享一个待分配卡和 Session

唯一映射必须同时包含外部会话和已授权执行范围，不能只使用群名或某个消息发送人的昵称。

建议绑定键由下列字段组成，编码方式由实现确定：

    app_id + app_user_id + platform_id
      + conversation_type + conversation_id + executor_binding_id

- `app_user_id`：固定的已认证执行设备实例；第一版不自动跨设备转移。
- `platform_id`：Router 中的平台租户/应用配置标识，不能仅使用 feishu/dingtalk 字符串。
- `conversation_type / conversation_id`：群或私聊及其稳定外部会话标识。
- `executor_binding_id`：Router 验证后的执行身份绑定。字段名为建议，不等于任意一个 sender ID。
- `thread_id`：用于关联请求、补充和原话题回传，第一版不参与创建多个 Flux Session。

第一版沿用“明确用户/成员授权下的执行设备”边界。同一个群若向两个不同用户的个人执行身份发起工作，不能将两人的私有任务合并到同一卡片。若以后增加团队共用执行身份，可在该明确授权范围内共享映射；本方案不默认开放全群调用任意成员的电脑。

### 2.2 范围与不做事项

| 第一版纳入 | 第一版不纳入 |
|---|---|
| 群首次请求的待分配入口；Project 和 Agent 两种归属 | IM 中的 Session 列表、新开/切换 Session |
| 固定会话、多任务串行、来源标识 | 自由认领任务池、自动多设备选主/迁移 |
| 持久化、去重、重启恢复、控制与审批衔接 | 多 Agent 自动分工、A2A 编排 |
| 原群/原话题的状态和授权结果回传 | 自动上传整份本地目录、公开完整执行日志 |
| 同工作目录冲突保护和明确等待状态 | 未隔离条件下的同目录并行写入 |
| 统一数据模型预留私聊 | 在私聊会话 ID 契约未明确前宣布私聊全面兼容 |

首个端到端验收使用一个平台的测试群；推荐先飞书，因为现有对接文档的群链路以飞书为主。钉钉仍须完成同一契约的适配和独立验收，不能由平台名称推断其能力。

## 3. 完整用户流程

### 3.1 首次请求与待分配

1. 群成员真实 @Bot 并提出任务。
2. Router 验证平台事件、实际发送人、群访问关系、账号与设备绑定，并确定唯一执行端。
3. Flux 先幂等保存事件。首次合格执行请求创建一张待分配卡；普通群上下文不触发卡片。
4. 同一绑定范围的新请求追加到这张卡下，保留顺序和每条请求的来源，不重复要求用户分配。
5. Router/Flux 对来源显示“已收到，等待在 Flux 中选择 Project 或 Agent”；不得显示“正在执行”。

Flux 离线时，由 Router 持久化待投递事件并显示设备离线；客户端恢复后才形成可见的本地待分配卡，不能伪报本地已保存。未绑定账号或无权访问时，不向任意在线客户端广播。

### 3.2 分配归属

待分配卡展示平台、群名、发起人、首条请求摘要、后续请求数量与时间。用户展开后可查看待处理请求，选择本地有效的 Project 或 Agent。

主操作为“分配并开始”，旁边说明：本群在当前执行身份下的后续请求也会进入此归属。用户可以暂不处理；拒绝/停用应留下明确状态，重投旧事件不能反复生成卡片。

确认后：

1. 校验目标存在、未归档，执行设备和成员授权仍有效。
2. 固定分配操作 ID 与版本，幂等创建一个全新的专用 Session，不能复用个人默认会话或最近会话。
3. 持久化绑定、Session 和待处理请求的关系，并与 Router 完成幂等确认。
4. 确认完成后，按持久化顺序释放未过期、未取消、仍获授权的请求。
5. 卡片从“待分配”列表移出；专用会话出现在所选 Project/Agent 下，并显示外部来源标签。

选择 Project/Agent 不应自动提高工具权限；“分配并开始”只在既有授权和远程执行策略内启动，遇到敏感操作仍需确认。

### 3.3 后续任务

- 同群、同执行范围：始终解析到固定 Session。
- 不同平台话题：可以有不同回复位置，但不自动创建另一个 Session。
- 同一任务的明确补充：携带任务关联，进入当前任务的指导或后续处理。
- 普通新要求：进入队列；执行前读取已经提交的最新会话上下文。
- 当前任务等待审批/澄清：后续普通工作保持等待，审批或澄清答案走独立控制入口。

示例：先收到“修复登录问题”，再收到“修好后检查退出登录”。第二项排队，第一项的结果和执行状态提交后才开始第二项。若第一项失败，第二项不能自行假设“已经修好”，应说明前置条件未满足并等待决定或按明确要求继续诊断。

## 4. 当前实现与改造缺口

以下路径相对 OpenFlux-Rust 仓库根目录；符号名优先于可能随代码变化的行号。

| 位置 | 当前检查到的实现 | 本次需要的变化 |
|---|---|---|
| `gateway/src/gateway/standalone.ts`：`getRouterSessionId`、`setupRouterMessageHandler` | Router 入站复用按标题寻找的 `Router Messages`，直接进入执行路径 | 改为接收落库、绑定解析、待分配与统一任务提交 |
| `gateway/src/gateway/router-bridge.ts`：`RouterInboundMessage` | 基础消息带平台、发送人、内容和 metadata，没有完整的通用会话/归属契约 | 版本化规范化消息，明确来源和执行资格 |
| `standalone.ts`：`lastRouterUser` 与 `notify_user` 注册 | 主动通知依赖全局最后发送人 | 新远程任务必须使用任务级回复上下文，缺失时拒绝隐式发送 |
| `standalone.ts`：`LocalEntity`、`resolveSessionLocalEntity` | Session 的 `agentId` 实际兼容 Project 或 UserAgent 的归属 ID | 沿用内部解析，新增显式 `ownerKind/ownerId` 绑定元数据 |
| `gateway/src/sessions/turn-queue-store.ts` | 按 Session 持久化排队，支持 submissionId 去重 | 复用队列，补充外部任务关联和恢复入口 |
| `gateway/src/gateway/execution-registry.ts` | 同 Session 串行、执行身份关联和取消 | 复用；不能当作已有 Project 级互斥 |
| `standalone.ts`：`PendingInteractiveTurn`、`executeQueuedChatTurn`、`hydratePersistedQueue` | 提交、事件、恢复与澄清续接仍依赖桌面 GatewayClient | 抽取无 UI 连接依赖的服务与事件出口 |
| `standalone.ts`：`handleChat`；`gateway/src/gateway/goal-orchestrator.ts` | 活跃 Goal 占用 Session，新提交返回 `goal_active` | 新远程请求持久化等待；不得伪装内部续接绕过占用 |
| `gateway/src/gateway/user-input-coordinator.ts`、`gateway/src/work/*` | 已有澄清、审批及 Goal 状态机制 | 沿用原状态机，增加授权后的远程控制适配 |
| `src/gateway-client.ts`、`src/sidebar/new-conversation.ts`、`src/chat/follow-up-controller.ts` | 已有归属选择、队列与控制交互基础 | 复用交互组件，新增待分配视图、来源和回传状态 |

特别注意：`TurnQueueStore` 某回合标记 completed，并不证明远程业务任务完成。等待输入、等待计划审批以及自动续接都可能跨多个回合。不能直接把一次回合结束事件翻译为“群任务已完成”。

## 5. 本地数据模型建议

### 5.1 ExternalConversationBinding：外部会话归属

| 字段组 | 内容 |
|---|---|
| 唯一身份 | `id`、`bindingKey`、`revision`、`generation` |
| 已验证来源 | 平台配置、会话类型/ID、群展示名、执行身份和设备 |
| 分配状态 | `unassigned / assigning / assigned / paused / disabled / target_missing` |
| 归属 | `ownerKind: project或agent`、`ownerId`、`sessionId`；未分配时为空 |
| 策略 | 允许的发起/控制范围、回传策略、有效期配置 |
| 审计 | 创建/更新时刻、分配操作 ID、分配人、暂停/失效原因 |

分配中的唯一约束必须保证同一 binding generation 只能对应一个专用 Session。不要靠 Session 标题寻找或恢复绑定。

### 5.2 ExternalTask：可追踪的外部工作

每条有效请求一条任务记录，同一卡片可以聚合多个记录：

- `taskId`、稳定 `logicalRequestId`、事件/消息 ID、投递 ID、绑定 ID、接收序号。
- 已验证发起人、执行身份、权限引用，以及排队时的绑定 generation/目标快照。
- 文本、附件引用、上下文引用；不把原始平台 JSON 当作执行指令。
- 操作类别与关联目标：普通提交、补充、停止、查询、澄清、审批等。
- `sessionId / submissionId / queueItemId / turnId / runId / goalId / approvalId` 的实际关联；按需产生，不强求一条任务只有一轮运行。
- `replyTarget`：原群/私聊、原话题、原消息和结果可见范围；后续消息到达不能覆盖它。
- 任务业务状态、恢复/失败原因、到期时间、授权复核结果。

Session 消息、任务输出、摘要及历史检索片段应保留 `source` 与 `contextVisibility`（建议字段）。至少区分群共享范围与仅本地可见范围；派生摘要/检索索引继承原资料的访问边界，不能在汇总过程中去掉限制。

同一逻辑请求的网络重投只能关联原记录。`delivery_id` 表示一次投递回执关联，不替代逻辑请求去重 ID。

### 5.3 ExternalOutbox：结果回传记录

保存发布 ID、任务 ID、目标、内容版本/哈希、状态、重试次数和平台真实消息回执。日志与公开回复必须分离，不能把原始工具结果直接作为群消息正文。

这些记录可复用或扩展现有本地持久化设施；需要恢复日志或事务保障。它们是来源、分配和交付账本，不应实现第二套 Agent 执行器。实际回合仍由现有 TurnQueueStore 与 ExecutionRegistry 调度。

## 6. 分配操作、排序与持久化

### 6.1 接收顺序

先验证、再持久化、最后 ACK。每个绑定生成稳定递增的本地接收序号；若 Router 提供有保障的会话序号，应采用明确的缺口/补齐策略。不能仅按客户端收到的墙钟时间或群消息展示时间排序。

历史导入、编辑通知、公开结果回显可保存为上下文，但不创建新的执行项。实时重复消息不会改变已有队列位置；待执行项被删除后要保留去重记录，不能由重投复活。

### 6.2 分配的可恢复流程

使用 `assignmentOperationId + expectedRevision` 和绑定级并发控制：

    unassigned → assigning
      → 本地幂等创建专用 Session、保存归属和任务关联
      → Router 幂等接受该归属版本
      → assigned → 允许调度

本地存储与 Router 不存在天然的跨进程事务，必须保留中间态并可重试：

- 双击或两个窗口同时分配，仅一个操作有效；另一个返回现有结果或版本冲突。
- 已创建 Session 后崩溃，恢复时根据操作 ID 找回同一个 Session。
- Router 确认回包丢失，查询或重试相同操作，不新建 Session、不重复放行任务。
- 分配期间到达的新请求继续持久化到原绑定，由同一顺序调度。
- 目标失效或授权撤销时停止放行，显示原因；不临时改用默认 Agent。

### 6.3 改绑和异常目标

第一版不提供 IM 改绑入口。Flux 设置中的改绑也仅在无运行任务、无未结束 Goal/审批、无待执行项时允许；否则先明确处理这些工作，不静默迁移。

安全改绑产生新 generation，并由系统建立新归属的专用会话；旧记录、旧会话、旧回传项保留原身份。用户仍不需要挑选 Session。

Project/Agent 归档、专用 Session 删除或目标目录失效时，绑定进入暂停/目标失效状态；需用户处理，不能自动新开会话继续执行。通用会话归属修改入口也必须检查远程绑定，不能绕过此规则。

## 7. 统一执行、上下文与控制

### 7.1 抽取无 UI 依赖的执行入口

建议从当前交互代码抽取 `TurnSubmissionService` 与 `ExecutionEventSink`（拟新增名称）：

- 桌面消息和 Router 消息都是提交适配器，共用持久化、权限判断、队列、执行、取消与续接。
- 不伪造 GatewayClient，也不通过直接调用 executeAgent 绕过统一队列。
- 后台 Gateway 能在没有打开聊天窗口/没有 UI WebSocket 的情况下恢复队列、发布状态、等待和接收授权答案。
- 桌面订阅和 Router 回传分别消费同一套持久化业务事件；任何一个出口断开不应丢失业务状态。
- 补充 `source: router` 或等价来源模型，不把远程请求冒充 local/cloud 内部输入。

### 7.2 串行与上下文

同一固定 Session 的普通远程请求顺序执行；本地在此专用会话输入的普通工作也进入同一调度顺序。不要在 Router 建立一条独立执行链，绕开本地已经运行的任务。

执行下一项前必须满足：前项的结果和事件已持久化、当前业务工作已释放 Session、权限和有效期复核通过。

待执行请求可以在 UI 中展示，但尚未执行的后续要求不能无意中变成当前任务的指令。每次运行构建有明确边界的上下文：已提交且对当前任务身份可见的会话历史、授权范围内的群背景、当前任务输入、明确批准的补充。

同一个 Session 不意味着所有消息都能进入远程模型上下文。本地备注及其派生内容默认仅本地可见，远程运行在读取历史、摘要和检索结果前统一过滤；只有用户明确将内容共享为该群任务的补充后才允许使用。不能只在最终发送阶段隐藏备注，因为模型此前读到的私人信息可能被间接复述。

长期 Session 使用任务完成摘要、决策与约束记录及按需历史检索维持连续性。摘要不能覆盖任务台账、权限状态和原消息引用，也不允许跨群混入私人会话历史。

### 7.3 Goal、审批和澄清

| 到达的事件 | 建议处理 |
|---|---|
| 普通新任务 | 空闲执行，否则持久化排队 |
| 活跃 Goal 期间的新任务 | 保存在外部任务账本的 `waiting_goal` 状态；Goal 结束或明确释放后只提交一次 |
| 明确补充当前 Run | 检查发起人权限与目标身份后走 steer；目标过期时不自动转投新 Run |
| 澄清答案/审批决定 | 精确关联请求、任务版本、授权人和有效期，走既有控制/续接方法 |
| 查询状态 | 只读，不恢复、不排队启动工作 |
| 停止当前任务 | 匹配 task/turn/run/goal 身份；第一版保守暂停后续普通队列并明确告知 |
| 取消某个排队项 | 只取消该项并保留去重记录，不影响正在运行的另一项 |

Goal 期间的等待记录是统一来源账本的一种未调度状态，不是第二条可并行执行的队列。Goal 多轮、自动续接、等待输入的优先级由统一服务协调；不能将一个中间 Turn 的结束当成释放整个任务。

普通“可以”“继续”不天然等于审批。只有明确关联到当前待确认项、权限通过的答复才能生效；不明确时询问或展示任务卡操作。即使模型识别了自然语言意图，结构化授权校验也必须在代码层执行。

### 7.4 同工作目录冲突

现有串行边界是 Session，不是 Project。多个群各自有 Session，或者用户在另一个本地会话工作时，仍可能访问同一目录。

第一版先采用保守规则：对可能写入 Project 工作目录的执行增加跨 Session 资源协调；无法可靠判断只读的 Project 任务按独占执行处理。资源身份需规范化并覆盖附加目录、重叠目录以及两个 Project 指向同一目录的情况。

本地与远程执行必须共同遵守该协调，不能只锁 Router 入口。未完成资源协调前，同工作目录的第二项写入请求应明确阻塞或要求隔离工作目录，不宣称已支持安全并行。Agent 若拥有目录写入工具，同样纳入实际资源权限和冲突判断。

## 8. 三组独立状态

| 状态维度 | 建议状态/意义 |
|---|---|
| 归属 | 未分配、分配中、已分配、已暂停、已停用、目标失效 |
| 任务执行 | 等待分配、排队、等待 Goal、等待资源、运行中、等待输入、等待审批、已暂停、完成、失败、取消、过期、待恢复确认 |
| 平台交付 | 待发送、发送中、已送达、可重试失败、发送结果未知、不可发送/权限失效 |

设备在线状态独立展示，不混入“是否绑定”。持久化 ACK 只代表保存成功；单个 Turn 完成不等于业务任务完成；业务任务完成不等于平台已经收到结果。

等待输入/审批期间保持任务未结束。运行中进程崩溃，标记待恢复核对并检查已有操作回执，不盲目重新执行有副作用的动作。未启动的有效任务可在复核后恢复队列。

待分配、离线和排队请求都应有可配置有效期及数量上限，超过后明确标记过期/拒收，不能静默丢弃，也不能第二天上线后无条件执行昨日失效要求。具体默认值在联调前确认。

## 9. Router 必须配合的契约

### 9.1 首次接入的循环依赖

现有 guide 的 group_collaboration.activate 关联成员与 Project，project_context.append 带 project_id，plan.generate 将请求交给发起人的 Project。文档没有定义“还没有 Project/Agent 归属时，如何先把请求交到 Flux”。

因此必须新增或扩展一条**不依赖已分配 project_id，但仍验证账号、设备、群关系和接收资格**的未分配投递路径。仅增加客户端待分配 UI 不能闭环，也不能用虚构默认 Project 绕过它。

### 9.2 需要共同确定的字段语义

| 契约 | 要求与当前缺口 |
|---|---|
| 通用外部会话标识 | 明确 conversation_id 与 channel_id 的映射、群/私聊类型、租户唯一范围、稳定性；现文档未完整定义 |
| 逻辑话题 | 保留 thread_id 与原消息关联；明确原生/合成规则、缺失时回传方式；不用于 V1 Session 分裂 |
| 执行身份 | 实际 sender 与 executor_binding 分开，由认证 Router 决定目标设备，Flux 二次校验 |
| 未分配投递 | target 可为空；仍有稳定绑定范围、来源和投递回执，未分配 ACK 不强求 session_id |
| 互斥归属 | target_kind=project或agent、target_id；不能把 Agent ID 塞进 project_id 冒充 Project |
| 分配确认 | 操作 ID、expected revision、绑定 generation、明确业务结果与可重试查询 |
| 请求身份 | 跨 append、plan.generate、work_order 的 logicalRequestId、阶段和任务关联 |
| 执行资格 | 真实触发、授权范围、history_import、suppress_agent_execution、回显类型必须可验证 |
| 控制 | task/run/approval/Goal 身份、决定版本、操作人、有效期；拒绝迟到或越权操作 |
| 回传 | taskId、稳定 replyTarget、发布 ID、内容版本、平台真实发送回执 |
| 能力协商 | 明确新能力和协议版本；无能力客户端不得被送入新式待分配自动执行流程 |

首次投递后的分配只是释放原请求，不生成第二个逻辑任务。同一请求若经上下文追加、计划处理、工作单控制多路到达，只有约定的执行阶段能启动一次；上下文同步不能同时启动另一轮。

新能力建议暂名 `external_conversation_assignment_v1`。这只是方案占位名称，需 Router 同事确认；不能提前声明客户端已经支持。

### 9.3 归属扩展不能只改一个字段

现有群接口多处依赖 project_id。支持 Agent 目标时，需要共同检查目标注册/激活、成员关系、附件/历史授权、工作单和结果回传的校验链。若某项能力仍仅支持 Project，应按能力明确拒绝，不能让 Agent 借用其他 Project 的身份访问。

无稳定外部会话 ID 或不能证明执行资格的消息，不得启用新的群自动执行路径。旧私聊可按明确的兼容策略保留，但不能用全局 Router Messages 作为新版群任务的静默降级。

## 10. 回传与权限

### 10.1 消息策略

默认回原群/原话题的任务状态与授权摘要，不逐个私发群成员、不默认 @所有人。进度优先更新同一张卡；关键等待、失败和完成可发通知，不输出逐 Token 内容或每一步工具日志。

未分配阶段可按会话聚合状态，避免连续请求重复刷屏；每条任务仍保留自己的回复位置。平台没有话题能力时，Router 应明确采用引用原消息或带任务编号的群回复策略，不能擅自改为个人私信。

### 10.2 可见性不等于控制权

分别保存发起人、执行设备所有者、授权控制者和结果可见范围。群成员能看到公开结果，不等于能访问整份 Project 或批准本机操作。

有效执行权限取本地权限、远程绑定授权及当前操作授权的交集。个人会话的 full access 设置不能自动变成全群的执行权限。排队任务在开始和敏感动作前复核必要权限；成员移除、解绑和撤权后不得继续放行旧请求。

共享 Session 中不同任务仍使用各自的操作身份。来自某人私人连接的数据不得因为保存在这个 Session 中就向其他任务发起人披露；不能安全区分的私人连接或资料读取应限制在专门的个人流程中。

自动回群只允许明确适合公开的摘要和已授权成果。原始工具日志、本地路径、凭据、私人文档全文不自动发送；敏感或无法确定分享范围的结果等待执行者审核。文件生成在本地与群成员已经能访问文件是两个不同状态。

### 10.3 可靠交付

业务结果先持久化到 Outbox，再经 Router 发送。发送失败仅重试交付，不重跑 Agent。所有重试沿用同一发布身份，并记录实际平台消息 ID。

平台发送成功但确认丢失时属于“发送结果未知”，优先查询/对账；不支持平台幂等或查询的情况下采用明确补偿或人工确认，不能承诺跨平台天然恰好一次发送。机器人公开回显只同步显示，不重新生成执行任务。

运行时的 notify_user 等主动消息工具必须获取当前任务的回复上下文和可见范围；缺少上下文时要求明确授权目标，不能回退到最后发消息的人。

## 11. 客户端界面

### 11.1 待分配入口

在侧栏增加轻量“待分配”入口及数量；无内容时可隐藏或不显示角标。收到消息只更新未读，不强制切换当前会话，不弹阻断式窗口。

卡片示例：

    飞书 · 研发群                         待分配
    张三：请检查登录失败的问题
    还有 2 条待处理请求
    归属：[选择 Project 或 Agent]
    本群后续请求也将进入该归属。
    [暂不处理] [分配并开始]

没有可选目标时显示创建 Project/Agent 的入口，创建后返回同一卡片，不偷偷分配给默认助手。

### 11.2 分配后的专用会话

- 位于所选 Project/Agent 下，标题可为“飞书 · 研发群”，改群名只更新展示，不改变绑定主键。
- 会话顶部展示来源、归属、执行状态及待执行数量。
- 队列项展示发起人、请求摘要、状态，可展开原消息/话题。
- 复用现有队列组件及审批/澄清交互，精确操作某项任务。
- 本地输入默认仅本地可见，不进入后续远程任务的历史、摘要或检索上下文；用户明确“补充到群任务”后才共享指定内容。只有带远程任务回复上下文的输出或明确“发送到群”的动作才对外发送。
- 任务执行状态和“结果尚未送达平台”分别呈现。
- 不显示 IM Session 选择器，不因每个话题创建多个侧栏会话。

## 12. 实施分工与阶段

以下为建议模块边界；可按项目现有组织方式合并，不要求机械增加全部文件。

| 阶段 | OpenFlux 工作 | Router 配合 | 完成门槛 |
|---|---|---|---|
| P0 契约冻结 | 确定来源、归属、身份、任务/控制/回传模型和测试样例 | 未分配投递、通用会话 ID、Project/Agent 目标、幂等与能力协商 | 双方样例覆盖未分配和已分配路径，无 project_id 循环依赖 |
| P1 接收与分配 | ExternalRequestStore、ExternalBindingStore/Service，待分配视图、原子分配与恢复 | 提供测试投递及分配确认 | 重投、并发点击、重启后仍是一张卡、一个 Session；未分配不执行 |
| P2 统一执行 | 抽取 TurnSubmissionService/EventSink，复用队列、上下文、Goal/澄清控制；加入资源冲突协调 | 精确控制和执行阶段身份 | 无 UI 连接可执行/恢复；顺序、上下文、权限及目录冲突测试通过 |
| P3 回传与交互 | ExternalOutbox、任务级回复上下文、状态和成果审核 | 幂等发布、平台回执、原话题回复 | 执行和发送状态独立；失败不重跑、不串群、不循环 |
| P4 联调与兼容 | 回归本地聊天、Agent、Project、Goal、审批、队列、重启；双平台适配测试 | 测试群、平台能力和兼容路径 | 下节必测用例通过，确认测试产物无敏感泄露 |

现有 Router 入口在适配后逐步切换；旧存量 Router Messages 保留为历史，不根据混合历史猜测其群归属或自动迁移到新绑定。新版本仅处理切换后或带稳定身份重投的请求，旧历史不执行。

## 13. 验收清单

| 编号 | 场景 | 预期 |
|---|---|---|
| A01 | 账号/设备已绑定、群尚无归属，首次真实 @ | 正确 Flux 出现待分配卡；模型和工具执行次数为零 |
| A02 | 未绑定账号、伪造 @、无权成员 | 不投递到任意个人设备、不创建执行任务，有明确受限状态 |
| A03 | 未分配时连续三项请求，首项被重投 | 一张卡、三个有序任务；重投不增加数量 |
| A04 | 普通群消息、历史 @、机器人回显 | 不创建卡片或运行，只按允许范围作为上下文 |
| A05 | 同名群、跨租户相同 ID、同群不同执行身份 | 绑定、Session、权限和结果互不串线 |
| A06 | 分别选择 Project 和 Agent | 均创建一个新的专用 Session，不使用私人默认/最近会话 |
| A07 | 双击分配、两个窗口选择不同归属 | 一个确定结果或版本冲突，没有重复 Session/重复执行 |
| A08 | 分配创建 Session 后崩溃、Router 确认丢失 | 同操作恢复到同一 Session；未确认前不执行 |
| A09 | 分配期间又到两项请求 | 不遗漏，按确定顺序进入固定 Session |
| A10 | A 执行时 B 到达，B 依赖 A 的结果 | B 排队，在 A 结果提交后读取最新上下文；A 失败不假装成功 |
| A11 | 用户说“新任务”、平台产生新 thread_id | 只新增任务或关联回复位置，不创建第二个 Session |
| A12 | 同一逻辑请求经过 append/plan/work-order 多路投递 | 只有一次有效执行，分配也不重复生成任务 |
| A13 | 普通任务排队时收到补充、查询、停止、审批 | 控制不死锁在队尾；迟到停止不取消接替运行的新任务 |
| A14 | 活跃 Goal、等待输入或等待审批时收到新工作 | 请求可靠保存、正确等待；中间回合结束不误报业务完成 |
| A15 | 关闭 UI 连接但 Gateway 运行，或 Gateway 重启 | 不依赖打开聊天页才能恢复；审批保持可处理或明确等待 |
| A16 | 同 Project 多 Session、重叠工作目录 | 写入冲突被串行/阻塞或隔离，不宣称已有安全并行 |
| A17 | 待执行期间撤权、解绑、任务过期或目标归档 | 不自动开工；状态明确，用户知道如何处理 |
| A18 | 执行完成、平台发送失败 | 仅重试 Outbox，Agent 和副作用执行次数不增加 |
| A19 | 平台已发送但 ACK 丢失 | 同发布身份对账；未知状态可见，不盲目新发或重跑 |
| A20 | 多任务来自不同话题，后来又有新发送人 | 各任务回原话题；主动通知不依赖 lastRouterUser |
| A21 | 群成员尝试批准他人电脑敏感动作 | 根据显式授权拒绝或请求正确审批人确认 |
| A22 | 敏感结果、私人连接内容；本地写入备注后再发起群任务 | 不自动群发；后续远程运行也不能通过历史、摘要或检索读取/复述私人备注，明确共享后才可使用 |
| A23 | 忙碌时改绑、专用 Session 删除 | 阻止静默迁移/重建，保留原任务归属和审计 |
| A24 | 老客户端或缺少稳定会话字段 | 新功能不静默降级执行，给出明确能力/升级提示 |
| A25 | 队列持久化、取消后重投、运行中崩溃 | 不丢待执行项、不复活已取消项；副作用未知时先核对再恢复 |
| A26 | 接入改造后的原本地功能回归 | 普通聊天、Agent/Project 归属、队列、Goal、审批和取消行为不退化 |

验证分三层：存储/状态机单元测试，模拟 Router 与 Gateway 的契约集成测试，最后使用测试 Router 和真实测试群端到端验证。对敏感操作用临时测试目录和可控副作用，不能拿用户真实项目或生产发布验证。

## 14. 联调前需要确认的参数

产品流程不再以“是否每个 @ 新开会话”为待定项；固定会话和排队已确定。剩余需要双方对齐的是工程契约：

1. 群/私聊 conversation_id、executor_binding_id、logicalRequestId 的稳定来源及唯一范围。
2. 未分配投递、分配确认、未分配 ACK、目标注册和 Agent 相关授权的实际 action/schema。
3. 哪个执行阶段拥有唯一开工权，如何与既有 plan/work-order 关联而不重复执行。
4. 各平台是否支持卡片更新、原话题回复、发布幂等或消息查询，以及缺失能力时的保守处理。
5. 待分配/离线/排队有效期、数量上限、权限复核时机、结果和去重记录保留期限。
6. 最初启用的测试用户、设备、群和能力开关；团队共享执行身份不默认启用。

## 15. 交付与变更约束

- 本阶段交付物是本方案文档，不表示相关能力已经实现或完成测试。
- 保留原 `docs/router-integration-guide.md` 不变，方便 Router 同事对照现有契约。
- 后续实施应在双方契约确认后逐阶段推进，保护当前工作区已有改动。
- 未经另外授权，不提交/推送文档或代码，不修改线上 Router、不更改更新清单、不发布客户端或官网。
- 联调样例和测试日志不得包含真实账号凭据、客户资料、画布图片或完整私人会话。

最终产品规则：**首次请求触发待分配，分配一次后会话固定；多条任务共享该授权会话的上下文并顺序执行，控制与回传始终绑定到具体任务。**
